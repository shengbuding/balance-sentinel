# 钱包哨兵架构修复设计

**日期：** 2026-08-05  
**基线：** `4495ac86d2c92592e7c90afecf0484a31286277c`  
**状态：** 已获用户逐节确认  
**执行方式：** Subagent-Driven Development，行为级测试先行

## 背景

前一轮安全加固已经收紧网络、脚本、WebView、备份和发布边界，但全量架构审查确认，应用仍存在一组会损坏数据、制造错误成功状态、导致后台能力失效或使设备上的升级不可用的设计问题。

本轮不是在现有 SharedPreferences 和 Service 结构上继续局部打补丁，而是按风险顺序建立稳定的数据、调度和界面生命周期边界。每一阶段都必须可以独立验证、提交和回滚。

## 目标

1. 任何账户、导入和迁移操作在崩溃、磁盘错误或进程终止后都能恢复，不产生用户可见的半提交状态。
2. 账户 JSON 损坏时停止写入并保留原始数据，不把损坏误判成空账户列表。
3. 将大规模历史、摘要、用量和运行记录迁移到 Room，消除整库 JSON 复制和同步提交。
4. 让手动刷新、后台任务、前台监控和 Widget 使用同一套类型化刷新结果。
5. 让系统调度负责可恢复后台工作，前台服务只承担用户明确开启的持续监控。
6. 让导航、权限、下载和页面状态遵循 Android 生命周期，进程重建后保持一致。
7. 补齐中文和英文、Widget 空态、大字体及无障碍行为。
8. 缺少正式签名配置时阻止 Release 产物生成，保证设备上的覆盖升级能力。

## 非目标

- 不改变钱包余额、用量和告警的核心产品含义。
- 不恢复已经脱敏或不存在的凭据。
- 不把 APK SHA-256 或签名预检纳入本轮功能修复。
- 不修改 Console 会话 TTL 对系统时间回拨的处理。
- 不为了迁移一次性重写全部界面视觉样式。
- 不嵌套创建新的 Git worktree。

最后两项安全问题继续记录在审查报告中。它们当前不破坏设备核心功能，按用户确定的范围不进入修复计划。

## 已确认的阻断问题

1. 备份导入保留旧 `revision`，不会可靠地使缓存和旧预览失效，也不经过完整账户生命周期清理。
2. 账户删除或替换先修改关联存储，最后才提交账户列表，任一步失败都会留下半迁移状态。
3. 启动迁移先写入新账户编号，后续失败无法回滚，并遗漏部分关联存储。
4. 账户 JSON 解码失败返回空列表，后续正常写操作可能覆盖原凭据。
5. 约 90,000 条历史记录保存在单个 SharedPreferences JSON 中，刷新会整库读取、复制、序列化和同步提交。
6. 后台服务丢弃逐账户结果，并把旧缓存当成本次成功。
7. 前台服务脱离前台后依赖普通后台 Handler，健康任务和午夜任务不能可靠恢复。
8. 服务状态由配置值反推，在没有存活证据时仍可能显示运行。
9. 导入缺少事务、输入上限和陈旧预览检测。
10. 多条网络响应路径在应用限制前无界读取整个响应体。
11. 首页刷新时间和加载状态全局化，并发完成时会互相覆盖。
12. 导航缺少系统返回栈、重建恢复和完整深链处理。
13. 下载取消不取消协程和网络调用，重试会并发写同一路径。
14. 通知权限拒绝后相关功能仍显示有效，首次启动权限请求时机不合理。
15. 数据管理页在冷启动主线程扫描完整存储。
16. 币种未在信任边界统一规范化。
17. 英文本地化、Widget 空态、大字体和无障碍不完整。
18. Release 缺少正式密钥时回退 Debug 签名，生成的产物可能无法覆盖升级。

## 总体架构

最终结构分为五层：

1. `CredentialStore`：保存 API Key、额外凭据、Console 会话和其他敏感配置。
2. Room 数据库：保存账户元数据、活动凭据代次引用、历史、摘要、用量、刷新结果和持久化操作台账。
3. 领域协调器：提供账户生命周期、导入、迁移和刷新提交的唯一原子可见边界。
4. 调度层：使用 WorkManager 承担可恢复任务，使用前台服务承担显式持续监控。
5. 表现层：从持久化领域状态派生页面状态，不根据控件或配置值猜测后台事实。

Room 与加密存储无法参加同一个物理事务，因此跨存储一致性采用“暂存、发布、清理”协议。用户可见状态只在 Room 事务中切换；发布前的新凭据不可见，发布后的旧凭据只是可重试清理对象。

## 数据层设计

### Room 数据库

第一版数据库至少包含以下职责：

- `accounts`：稳定账户 UUID、显示顺序、标签、Provider、非敏感配置、活动凭据代次、账户修订号和状态。
- `balance_records`：账户、规范化币种、采样时间、余额、用量和来源。
- `daily_summaries`：按日期、账户和币种聚合的数据。
- `usage_snapshots`：刷新产生的用量快照。
- `refresh_runs`：一次手动、后台、前台或 Widget 刷新的总体运行记录。
- `refresh_account_results`：逐账户结果、数据时间、错误分类和重试信息。
- `mutation_operations`：导入、账户替换、删除和迁移的持久化阶段台账。
- `app_metadata`：本地单调修订号、迁移状态和活动数据代次。
- `app_settings`：可导入的全局设置、后台刷新周期和前台会话周期。
- `account_alert_settings`、`notification_wallet_selections`、`alert_runtime_state`、`snooze_state`：带账户外键的设置和运行状态。

历史表按 `(account_id, currency, recorded_at)` 建索引，摘要表使用 `(date, account_id, currency)` 唯一键。列表和图表必须使用分页、范围查询或数据库聚合，禁止重新读出全部历史后在内存筛选。

### 稳定身份

账户 UUID 是所有关联数据的唯一身份。显示编号只表示排序，不参与存储键、通知身份或迁移映射。重新排序只更新 `displayOrder`，不会迁移历史、摘要、用量或凭据。

币种在网络响应、脚本结果、导入文件和用户输入进入领域层时统一转换为大写 ISO 4217 代码。未知代码返回明确验证错误，不写入数据库。

### 凭据读取

`CredentialStore.read(accountId, generation)` 返回以下封闭结果之一：

- `Missing`：对应键不存在。
- `Valid`：完整解码并通过结构校验。
- `Corrupt`：原始内容存在但无法认证、解密、解码或校验。

`Corrupt` 永远不能转换为空账户、空凭据或默认配置。任何依赖该凭据的写操作必须停止，并向上返回数据损坏错误。原始加密值保留，直到用户明确完成恢复、导出或重建。

### 可恢复提交协议

新增、编辑和导入使用以下顺序：

1. 创建不可变操作 ID，并在 `mutation_operations` 记录目标、基线修订号和 `PREPARED` 阶段。
2. 在任何外部写入前，把本次全部 staged generation 清单持久化到操作行。generation key 由 operation ID 和 account ID 确定生成。
3. 将新凭据写入新的、尚未被任何账户引用的 generation。
4. 完整读回并验证暂存凭据。
5. 在单个 Room 事务中写账户及关联数据、切换活动 generation 引用、递增本地修订号，并把操作标记为 `PUBLISHED`。
6. 返回成功。此时用户只能看到完整新状态。
7. 清理旧 generation，并把操作标记为 `COMPLETED`。

若在发布前失败，删除暂存 generation，旧状态保持可见。若在发布后清理失败，新状态仍完整可用，恢复任务只需继续幂等清理。

删除账户时，Room 事务先原子删除或归档账户及其受拥有关系约束的数据，并递增本地修订号。事务成功后再清理已不被引用的凭据。凭据清理失败不会让已删除账户复活，也不会破坏其他账户。

每一步都必须幂等。应用启动时只恢复未完成操作，不重复已经确认的副作用。

### 导入协议

导入分为解析、预览和应用三步：

1. 流式读取并同时执行字节数、记录数、单字段长度和结构深度限制。
2. 完整解析后生成不可变导入计划，列出新增、更新、保留、删除、冲突和跳过项。
3. 计划包含当前本地修订号及计划内容摘要组成的基线指纹。
4. 应用前重新计算基线指纹。任何账户或相关设置在预览后发生变化时，计划以 `StalePlan` 失败并要求重新预览。
5. 所有新凭据先暂存并验证，然后通过一次 Room 事务发布账户、关联数据和新的本地修订号。
6. 备份文件中的 `revision` 只作为来源元数据保存，绝不覆盖本地修订号。

配置备份和历史数据分别设置保守硬上限，并通过测试固定上限行为。实现必须使用有界流读取，不允许先 `readBytes()` 再判断大小。超限不会产生任何持久化副作用。

### 旧数据迁移

迁移使用持久化、可重入阶段：

1. `DISCOVERED`：只读识别旧账户、历史、摘要、用量、日志和关联设置。
2. `VALIDATED`：完整解码并校验身份、计数、币种和数据范围。
3. `CREDENTIALS_STAGED`：为每个账户写入并读回新凭据 generation。
4. `ROOM_WRITTEN`：在 Room 事务中批量写入全部数据，但尚不删除旧数据。
5. `VERIFIED`：重新查询目标表，核对计数、关键字段和摘要。
6. `ACTIVE`：切换活动数据代次并记录新的本地修订号。
7. `CLEANED`：延迟删除旧数据。

任意阶段崩溃后从持久化阶段继续。只有 `VERIFIED` 成功后才允许切换，只有 `ACTIVE` 成功后才允许清理。旧数据解码失败时迁移停止并保留原值，不创建空数据库状态。

### 大数据行为

- 历史导入和迁移使用固定大小批次。
- Room 写入在 IO 调度器执行。
- 首页、数据管理页和 Widget 只读取所需摘要。
- 导出使用游标或分页流式编码，不构造完整内存副本。
- 至少使用 90,000 条历史记录验证冷启动、查询、聚合、导入和导出。

## 刷新与调度设计

### 统一刷新引擎

手动刷新、后台任务、前台监控和 Widget 都调用同一个 `RefreshEngine`。引擎返回逐账户类型化结果，不直接伪造总体成功。

逐账户结果至少包括：

- 成功，并携带本次数据和数据时间。
- 认证失败。
- 网络失败及是否可重试。
- 限流及建议重试时间。
- 响应结构无效。
- 脚本策略拒绝或脚本超时。
- 账户在执行期间已变化。
- 持久化失败。
- 用户取消。

批量结果只能是全部成功、部分成功、全部失败或取消。旧缓存可以继续展示，但必须保留原数据时间，并标记陈旧状态和本次失败原因；旧缓存不能转换成本次成功。

每个账户的余额记录、用量、事件日志和 `refresh_account_results` 终态在同一个 Room 事务提交。批次总体结果只从已经提交的逐账户终态派生。启动恢复把没有活动 owner 的 `RUNNING` 运行标记为 `Interrupted`，避免永久加载或虚假成功。

每个账户只允许一个有效刷新代次。旧请求晚返回时不得提交。取消必须传播到协程、脚本执行和 OkHttp `Call`。

### WorkManager

引入 WorkManager 管理：

- 普通周期刷新。
- 下一次本地午夜维护。
- 健康检查和异常后的有限重试。
- 开机、应用升级和进程重建后的持久任务恢复。

所有逻辑任务使用稳定唯一名称。重复启用只更新已有任务，不创建平行调度链。可恢复错误采用有上限的指数退避和随机抖动；认证、解析和策略错误不自动重试。

设置模型分离后台周期和前台会话周期。后台周期只能关闭或不小于 WorkManager 的 15 分钟下限；更短周期只用于用户主动开启的有界前台会话。旧版小于 15 分钟的值迁移为对应前台周期，并把后台周期设为 15 分钟保底。界面同时展示期望周期和当前实际周期。

午夜维护使用一次性 WorkRequest。每次执行结束后根据当前时区计算下一个本地午夜并重新注册，因此时区或夏令时变化不会永久漂移。任务允许被系统延迟，但不能丢失；业务逻辑必须按待处理日期幂等补做。

### 前台持续监控

只有用户明确启动监控会话时才启动前台服务。服务存活期间始终保留合法前台通知，不再调用 `STOP_FOREGROUND_DETACH` 后依赖普通 Handler。

当前服务类型是 Android 15 的 `dataSync`，每个应用在滚动 24 小时内最多使用 6 小时。持续监控因此定义为有界、用户发起的前台会话，而不是系统不允许保证的永久常驻。实现必须在预算耗尽前主动结束，并处理系统 `onTimeout` 回调：停止工作、移除前台状态、写入 `PlatformLimited` 或 `Paused`，不得立即重启消耗已用尽的预算。普通后台刷新继续由 WorkManager 以系统允许的至少 15 分钟周期执行。

小于 15 分钟的刷新间隔只在活动前台会话内有效。会话结束、预算耗尽或平台拒绝启动时，界面必须显示实际能力已降级，不能继续显示原间隔正在运行。

服务只负责持续监控时钟、存活租约和调用统一刷新引擎。普通后台任务不依赖服务存活。

旧版午夜、健康、Widget 和启动重试 Alarm 全部在升级协调阶段取消。迁移完成后不再申请 `SCHEDULE_EXACT_ALARM`，避免与 WorkManager 形成平行调度链。

状态分为：

- `desiredState`：用户是否希望持续监控。
- `observedState`：本次应用进程启动周期内是否有新鲜心跳和活动工作证据。

界面据此显示启动中、运行中、异常或已停止。配置值不能单独证明服务运行。进程重建后，旧启动周期的心跳立即失效。

### 有界网络响应

所有 Provider、脚本、更新检查和 Console 代理使用共享的有界响应读取器：

- 先检查状态码、Content-Type 和已知 Content-Length。
- 从流中按端点预算读取，不能在读取完成后才截断。
- 同时限制压缩传输体和解压后的有效载荷。
- 超限、超时和取消均关闭响应体并返回稳定错误类型。
- 日志只保留有界、脱敏诊断片段。

证书固定至少同时包含当前公钥固定和备用轮换固定。证书轮换期间任一合法固定可用，避免单一叶证书过期后使所有查询失效。固定失败时明确报错，不降级到未固定连接。

## 导航、权限与界面状态

### 导航

使用单一 Compose `NavHost` 和类型化路由。系统返回键、应用栏返回按钮和深链进入共享同一返回栈规则。

深链参数在进入目标页面前完整解析并校验。缺失、无效或指向已删除账户的深链进入明确错误状态，不回退到任意账户，也不展示空白页。

`SavedStateHandle` 只保存筛选、选中 ID 和页面位置等轻量界面状态。账户和历史等业务对象在重建后从 Room 重新加载。

### 首页状态

首页按账户保存刷新状态：请求编号、是否加载、最近成功时间、当前数据时间、陈旧状态和错误。全局加载状态只从逐账户状态聚合。

每次请求带递增编号。只有仍是当前编号的完成事件可以更新对应账户，旧请求晚完成不得清除新请求的加载状态或覆盖新数据。

一次性提示和导航使用事件通道，避免 Compose 重组或页面恢复时重复消费。

### 权限

首次启动先让用户进入应用。通知权限仅在用户启用通知、提醒或持续监控时按上下文申请。

权限模型区分：

- Android 版本是否需要运行时通知权限。
- 通知权限是否已授予。
- 精确闹钟能力是否可用。
- 当前系统是否允许目标前台服务行为。

权限拒绝后，相应开关显示未授予或受限，不能继续显示为有效。永久拒绝时提供系统设置入口。重新获得权限后由持久化期望状态恢复相应任务。

### 下载生命周期

每次下载使用唯一操作 ID 和独立 `.part` 文件。同一版本或同一目标只允许一个活动下载者。

取消同时取消页面协程、WorkManager 工作和 OkHttp `Call`，然后只删除本次操作拥有的临时文件。重试创建新的操作文件，不与旧任务并发写入。

下载完成后先完成内容长度和结构完整性检查，再在同目录原子移动为可安装文件。失败或取消不会覆盖已有可用文件。下载状态持久化，页面重建后继续显示真实进度和结果。

APK SHA-256 和签名预检不在本轮范围；Android 包管理器仍负责最终安装签名检查。

### 数据管理

数据管理页冷启动只查询统计摘要和首屏分页数据。完整扫描、导出和校验在 IO 调度器执行，提供可取消进度。破坏性操作只有在领域事务完成后才显示成功。

## Release 签名

Debug 构建继续使用 Debug 签名。Release 产物任务必须提供完整正式签名配置；当任务图包含 assemble、bundle、package、install 或 publish Release 产物时，缺少文件、字段或密钥必须在任务执行前以明确错误失败。纯 `compileReleaseKotlin`、Release 单元测试和 Lint 不生成可分发产物，可以在无密钥开发机运行。

Release 禁止回退 `signingConfigs.debug`。CI 检查 Release 证书指纹是否为允许的正式证书。测试环境使用专用测试签名链验证同签名可以覆盖升级、异签名被系统拒绝。

## 本地化、空态与无障碍

- 所有用户可见文本进入字符串资源，补齐中文和英文。
- 日期、时间、数字、货币和复数使用系统区域格式。
- 禁止在 Kotlin 中拼接可见句子。
- Widget 分别处理未配置账户、无数据、陈旧数据、权限受限和刷新失败。
- 动态文本允许换行和滚动，不使用固定高度容纳可变内容。
- 最大系统字体比例下，关键数据和操作仍可访问。
- 图标按钮具有内容描述，交互区域至少 48dp。
- 状态不只依靠颜色表达，并验证对比度、焦点顺序和屏幕阅读器语义。

## 错误与日志模型

面向用户的稳定错误类别为：输入错误、权限错误、认证错误、网络错误、服务策略错误、数据损坏、存储空间不足和内部故障。

每个错误包含稳定代码、是否可重试和建议操作。界面不展示堆栈、原始响应或凭据。日志可以保存操作 ID、阶段和内部错误码，但必须移除 API Key、额外凭据、Cookie、完整响应、账户敏感字段和导入文件内容。

数据损坏、迁移失败和导入失败不触发自动重置。用户可选择重试、导出可恢复数据，或在明确确认后重建。

## 分阶段实施

### 阶段 1：数据安全和可恢复事务

引入 Room 基础设施、账户元数据、凭据代次和操作台账。先修复损坏读取、账户生命周期、修订号和导入事务，保证后续迁移有可靠落点。

### 阶段 2：Room 历史存储迁移

迁移历史、摘要、用量和日志，建立分页、批量和聚合接口，验证 90,000 条数据规模。

### 阶段 3：刷新结果和后台调度

建立统一类型化刷新结果，引入 WorkManager，收紧前台服务所有权、健康租约、午夜补做和有界网络响应。

### 阶段 4：导航和界面生命周期

引入 Navigation Compose，修复逐账户状态、权限时机、下载取消、数据管理冷启动和 Release 签名门禁。

### 阶段 5：本地化和无障碍

补齐字符串资源、Widget 空态、大字体、屏幕阅读器语义和界面恢复行为。

### 阶段 6：全量验证

执行完整单元、迁移、仪器、模拟器和可用实机测试，完成独立全量架构与对抗审查。

## 测试策略

所有行为修改遵循 RED、GREEN、REFACTOR。RED 必须能证明旧实现具有目标缺陷，不能只测试新辅助函数。

### 数据与迁移

- `Missing`、`Valid` 和 `Corrupt` 凭据读取。
- 损坏账户 JSON 后任何写操作都不覆盖原数据。
- 在可恢复提交每个阶段注入异常，验证旧状态或完整新状态可见。
- 删除、替换和导入的幂等恢复。
- 陈旧导入预览被拒绝，重新预览后可应用。
- 输入字节、记录数、字段长度和嵌套深度超限无副作用。
- 从每个已发布旧格式迁移，并在每一阶段模拟进程终止、磁盘满和重复执行。
- 90,000 条历史记录的分页、聚合、导入、导出和冷启动。

### 刷新与调度

- 全部成功、部分成功、全部失败和取消保持逐账户结果。
- 旧缓存在失败时保持陈旧，不变成本次成功。
- 同账户旧请求晚返回时不能提交。
- 取消传播到协程、脚本和网络调用。
- 重复调度不创建平行任务。
- 进程被杀、设备重启、应用升级、时区变化和断网恢复。
- 持续监控停止心跳后从运行中转为异常。
- 每条外部响应路径在预算处终止读取并释放资源。
- 当前和备用证书固定分别可用。

### 界面与设备

- 返回栈、进程重建、完整深链和无效深链。
- 多账户并发刷新状态隔离。
- 首次启动、权限拒绝、永久拒绝和重新授权。
- 下载取消、立即重试和页面重建。
- 数据管理页冷启动不执行完整存储扫描。
- 中文、英文、Widget 空态、最大字体和关键无障碍语义。
- 模拟器和可用实机上的安装、覆盖升级、通知、后台限制和长时间刷新。

### 构建门禁

- 单元测试和 Robolectric 测试。
- Room 数据库迁移测试。
- Compose 仪器测试和设备工作流测试。
- Debug 与 Release 编译、Lint 和差异检查。
- 缺少正式签名时 Release 构建按设计失败。
- 使用测试签名链验证覆盖升级行为。
- 每个任务完成后独立任务审查。
- 最终独立全量架构审查和对抗审查无新的 Critical 或 Important 功能问题。

## 完成标准

1. 四个阻断级数据损坏路径均有行为级回归测试并完成可恢复实现。
2. 历史主存储不再依赖单个 SharedPreferences JSON。
3. 所有刷新入口保存逐账户真实结果，旧缓存不会伪装成功。
4. 普通后台能力不依赖脱离前台的 Service 或进程内 Handler。
5. 页面重建、并发刷新、权限拒绝和下载取消均保持真实状态。
6. Release 缺正式签名时无法生成可分发产物。
7. 中文、英文、Widget 空态、大字体和关键无障碍工作流通过设备验证。
8. 两项 `SECURITY-ONLY` 发现保留记录但未混入功能修复提交。
9. 所有阶段测试、构建、Lint、差异检查和独立审查通过。
